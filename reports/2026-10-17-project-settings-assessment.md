# Project Settings: assessment and redesign

17 October 2026 · Pencils 0.15.18

## Conclusion

Project Settings needed a clearer information structure and a consistent editing model. The old page mixed project identity, organisation membership, teams, workflow, hierarchy and destructive actions in one form. Its toolbar then opened separate dialogs for related settings. Workflow appeared twice, and saving ordinary project details also submitted the workflow. Users had to remember both where a control lived and how its particular window behaved.

The redesign is implemented: a grouped navigation rail, ten focused pages, direct links, browser history, section-specific saves and source/rule editing sub-pages. Templates have been removed from settings navigation; existing template data is retained. The next substantial improvement should be guided integration setup and previews of the effects of configuration changes.

## Interaction contract

- The settings sidebar stays consistent across pages; the active page has an indicator. On smaller screens it becomes a labelled section selector.
- General, organisation/teams, workflow, hierarchy and fields have independent Save and Discard actions. Saving stays on that page. Discard reloads the current project data.
- Each settings page has its own URL. Source and automation editors also have nested URLs. Browser Back/Forward and reload work, and modified-click navigation can open another tab.
- Unsaved changes prompt before leaving. A pending save blocks navigation. A rejected concurrent save keeps the user's input visible rather than silently overwriting another change.
- Page load failures have an inline explanation and Try again. Saves report errors within the relevant form.
- Review dialogs remain appropriate for bounded actions such as source mapping preview, automation preview and version history. Ordinary settings editing stays on a page.
- Existing shared controls are reused: colour picker, workflow/hierarchy diagrams, team controls, source operations and automation operations.

## Verification and limits

The implementation is checked against isolated local fixtures, including real settings saves and a local Obsidian import/sync. Browser checks cover desktop and phone layouts, both themes, direct links/reload/history, unsaved-change protection, stale-revision rejection, independent schema preservation, import and automation creation/edit/preview. Existing navigation, source and visual-rule journeys are also exercised.

All 176 unit/API tests pass. The settings journey passes in Chromium and Firefox; automated accessibility checks pass across all ten settings pages on desktop and phone widths in both themes. Safari/WebKit was not run because its test browser is not installed. Read-only verification of deployed v0.15.18 in Argus 2.1 passed, with project settings, tasks and boards unchanged.

These checks do not constitute a live Jira or SharePoint connection test, a screen-reader audit or testing on physical iPad hardware. No real project configuration, task data or connected account is changed by the browser verification. The assessment is based on this application's implementation and UI, rather than new competitor or provider research.
