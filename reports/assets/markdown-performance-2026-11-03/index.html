Where large Markdown documents slow down

Pencils 0.21.54 · 3 November 2026 · production assets · 94 recorded browser observations

The hard limit is 200,000 source characters. Performance deteriorates well before it for dense formatting, large inline tables and syntax-highlighted code. Prose at almost the limit remains usable on this desktop. The sharpest failures are code highlighting in WebKit and searches that split highlighted code into thousands of DOM nodes.

Measured breakpoints

  • Plain writing: a 199,000-character document with headings opens in about 0.2 seconds and responds in about 40 ms on this desktop. A single 180,000-character prose paragraph also remains near the measurement floor. The CPU-throttled 180,000-character prose test reaches 144 ms, so the desktop result is not a phone guarantee.
  • Dense Markdown: mixed content reaches roughly 120 ms per key at 180,000 characters. A paragraph packed with links is already above 100 ms at 50,000 characters and reaches roughly 320 ms at 180,000. Density matters more than file size alone.
  • Inline tables: 6,000 cells take about 1.2 seconds to open; 19,998 cells take about 6.6 seconds and about 215–220 ms per cell keystroke. Under 4× CPU throttling, 12,000 cells take 11.6 seconds to open and about 638 ms per cell keystroke. A 20,004-cell table falls back to Source editing; the code's guard is 20,000 cells, header included.
  • Reading search over code: a 100,000-character JavaScript block, with 2,941 matches, takes 3.85 seconds for the common query and 10.00 seconds to clear those matches and find a unique term. At 180,000 characters the common query takes 11.58 seconds and the next query exceeds its 12-second action budget. The search already stops collecting after 5,000 matches.
  • WebKit code highlighting: 10,000 characters of JavaScript already produce about 193 ms code-keystroke response. At 100,000 characters opening takes 9.57 seconds and the case exceeds its 45-second total budget during the ten-keystroke phase. Two 180,000-character attempts fail to show the editor within 12 seconds. These are measured stalls/timeouts, not a demonstrated browser crash.

Highlighting control: cause, not just correlation

In separate temporary browser contexts, the Highlight constructor was made unavailable before app startup, exercising the existing uncoloured-code fallback. Production code and settings were unchanged.

The highlighted Reading cases retain 23,512 live DOM ranges at 100k and 42,336 at 180k, including the hidden editor's ranges. Search splits text nodes and later normalises them; browsers must maintain live range boundaries as the DOM changes. This source review, plus the fallback control, points to the interaction between syntax ranges and DOM mutation. Merely clearing the CSS highlight registry did not improve the timings: the module's painted map still retains its live Range objects. A preliminary skip-code-highlights diagnostic with an undefined registry generated a harness TypeError; it is excluded. Only the corrected no-highlight-api observations above are used as the control.

The editor/body check counts UTF-16 code units, including Markdown syntax but excluding metadata frontmatter; this is not a byte limit or a reliable word limit. A typical 200k English prose document is roughly 30,000 words. External oversized-file behaviour is a functional defect, not a useful larger-file mode.

Backend versus rendering

A warm, cached 200,000-character document took 3 ms to read and 9 ms to save through the loopback API (five observations each, including client serialisation and response parsing). This does not test concurrent users, a slow disk, VPN or reconnect. The measured multi-second failures are in the browser.

The ten-key typing tests normally issue ten whole-document PATCH requests. At about 199k characters that is roughly 2 MB of request data for ten inserted letters. The local server handled this test, but coalescing saves would reduce network traffic and revision/write work.

What to change first

  1. Bound syntax highlighting and stop mutating highlighted text for search. Use a token/range budget and visible-range highlighting, dispose old ranges, and give large code blocks a graceful fallback. Evaluate non-mutating search highlights and immutable ranges rather than keeping thousands of live DOM ranges through node splitting. Re-run the 100k/180k code cases in Chromium and WebKit.
  2. Make Live preview updates incremental. Cache block parsing by document revision, update dirty/visible ranges, and let caret/hover updates change only their small affected ranges. Replace nested linear blocked-range lookups with sorted/indexed intervals. Dense-link documents need a separate guard because one wrapped source line can contain thousands of widgets.
  3. Virtualise or page large inline tables. Avoid mounting every rich-text cell and measuring all cells per update. Index cells by ID and row, track dirty cells instead of scanning/serialising the whole table for one edit, and use Table documents for larger structured datasets.
  4. Create only the editor needed for the active mode. Reading should not retain an already-rendered Live table and its code ranges. Render long Reading sections lazily while preserving find and anchors.
  5. Coalesce network saves while keeping local recovery immediate. Keep offline durability, undo and conflicts intact; avoid ten full-body network writes for a ten-letter burst.
  6. Handle oversized vault files deliberately, then revisit the cap. Offer a usable read-only state and a path to split/reduce an external file. Raising the numeric cap alone worsens the workloads that already stall below it.

Method and limits

All documents were generated inside disposable vaults and served by the real Node server using the existing production build. Every case has a fresh browser context, reduced motion, a cold navigation within that context, and a 500 ms settling window after its first rendered frame. Main desktop comparisons have four independent observations; Source and Reading have two; the CPU-throttled, density sweep and WebKit cases are exploratory single observations unless the table shows repeats. The dense-link endpoints were repeated twice after their initial sweep.

Hardware: AMD Ryzen 9 9950X3D, about 59 GiB RAM. Chromium 149.0.7827.55 and WebKit 26.5. No other benchmark or test suite ran concurrently with the timing work. The full verification suite started afterwards. No real vault files, deployed assets or user settings were changed. No screenshots, images, Mermaid, maths, embedded-document graphs, server concurrency or physical iPad were stress-tested; those remain separate ceilings.

Timings come from ten trusted keyboard presses near the beginning of the document, three presses in the first table cell or start of a code block, real search controls, sampled scrolls and first-rendered-frame observations. Editing every possible document position was not tested. The legacy inputP50/inputP95 fields in raw observations measure a capture-listener microtask interval; they are not used as input-handler latency. GC is requested outside timed phases for Chromium heap comparisons. WebKit heap/long-task telemetry is unavailable and is not interpreted as zero cost. A case has a 45-second total budget; individual UI actions have a 12-second deadline. Failures retain their phase, and later runs retain partial opening/search timings.
