Document performance after F0.21-55 and F0.21-56

Recorded 3 November 2026. Production build, disposable vaults, before/after on the same Ryzen 9950X3D desktop. Baseline: 0.21.54. After: 0.21.55 with the 0.21.56 toolbar and WebKit scrolling follow-up. No user vault was modified by the benchmarks.

Changes

  • Markdown limit: 200,000 → 1,000,000 UTF-16 units. Inline table limit: 20,000 → 100,000 cells.
  • Large tables have bounded editable pages (at most 800 body cells plus the header); Reading and Live Find reveal a match's page. The complete model remains available for edits, formatting, CSV and Undo/Redo.
  • Code colours use at most 2,048 immutable ranges in a visible window. Text nodes are bounded to 2,048 UTF-16 units without splitting Unicode pairs. Reading releases its hidden Live editor components.
  • Block and inline parsing reuse unchanged content. Existing images, tables and code stay mounted during nearby edits. Images load lazily and decode asynchronously.
  • Word/character counts update locally. Every edit is kept immediately in browser recovery; short bursts share a network save.

WebKit scrolling follow-up

In 0.21.55, the 100,000-character code block still repainted slowly after Reading searches: about 1,165 ms at the 95th percentile for large scroll jumps. The 0.21.56 build measures 33 ms with syntax colours retained. A control that disabled caret hit-testing did not help; splitting the long text node did. Source text, selection and Undo are covered in Chromium, Firefox and WebKit. The scroll samples use two animation frames, so 33 ms is the harness floor.

Practical limits that remain

The file and cell caps are validation limits, not a guarantee of identical speed for every composition. An exceptionally dense 180,000-character single paragraph with thousands of links still takes around 1.5 seconds to open on this desktop and scrolls more slowly than ordinary paragraphs. At 100,000 cells, full-table Markdown serialization still makes a cell edit roughly 120 ms on desktop. Rich HTML tables, embedded documents and large images can add work and memory. Split long paragraphs and use a Table document for large spreadsheet workloads.

The WebKit profile is Linux WebKit with a 1,024 × 768 touch viewport at 2× resolution. The CPU4x profile is Chromium with fourfold CPU throttling. Neither is a measurement on the user's physical iPad 11 or Vivaldi; device memory, image decoding and server/VPN latency can differ. Find still caps displayed matches at 5,000.
