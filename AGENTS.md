# Project rules

## Consistency

Keep the interface consistent across all project views: Overview, Documents, List, Tree, Table, Kanban, Board, Calendar, Timeline and Capacity.

- Reuse shared components and styles for headers, navigation, menus and common actions. Improve the shared implementation instead of creating a separate version for one view.
- Keep common actions in the same positions, with the same names, icons and keyboard behaviour. Only view-specific tools should vary.
- Use the same spacing, typography, colours and interaction patterns, including light/dark themes and responsive layouts.
- Check affected views on desktop and mobile when changing shared UI. Preserve access to existing actions and settings.
- Use the shared sizing tokens in `public/controls.css` for buttons, fields and menu controls. Preserve Compact mode and 44px touch targets instead of introducing local heights.
- `controls.css` makes icon buttons square with `!important` in an `:is()` whose specificity is (0,2,1). A wider icon button, such as one with a text label, needs `!important` and a selector above (0,2,1), and a test that its content fits inside it.

- Keep the app as compact as Obsidian. Menus of rows (board menus, select menus, ⋯) use 4px padding (`--menu-panel-padding`) with their rows edge to edge and no gap, and prefer dividers to headings between groups; popovers that hold text or fields keep `--popover-padding` (8px). On desktop and iPad a setting with a one-line control is one row (name on the left, control on the right, a divider between rows; `project-settings.css`), and phones stack the name above the control; phones' View options keeps one row per field, name before control, in one font size (`--type-body`), with Clear filters as an icon left of Close in its header. Keep 44px touch targets and Compact mode.
- Give each action one home: don't repeat a bar control in its menu.
- Dropdowns open with the shared motion (`--menu-motion` in `controls.css`: a fade, a 4px drop and a grow, none with reduced motion): disclosures through the rule in `project-layout.css` (marked `data-user-open` by hand in `project-layout.js`), select menus and card editor pickers in `select-menu.css`. Add a new dropdown there, and hide its panel with `display: none` while closed, or the motion never starts.
- Use the shared colour picker from `public/color-picker.js` for every colour field: circular swatch, dropdown palette and custom hex editor.
- The top bar names only the open board or document, or the project when nothing is open, with no organisation or project crumbs (`public/topbar-title.js`, synced on navigation and renames). Phones show no title (the heading stays for screen readers) and no bar: the menu and New buttons float as round buttons, like Obsidian, with the toolbar row (`#view-toolbar`) between them.
- Settings live on one page (`public/project-settings.js`) with You, Organisation and Project sections, opened from the single Settings button at the bottom of the sidebar. Don't add settings dialogs or more settings buttons. Settings save as they change (`autosaveSettings`, with Saving…/Saved beside the page title), with no save bar or Save button; only Data sources, Automation and Import keep their own, since they set up connections, rules and files.
- In the toolbar row, the view switcher, search and filters sit on the left and the view's own controls on the right: a view's renderer returns `{ controls, html }` and `renderView` puts the controls in the toolbar's `.view-controls` slot; phones put them in View options, and a less-used option marked `data-filters-option` (Capacity's Measure, Scope and Team) waits in Filters on desktop and iPad, so the row stays one row. On desktop and iPad every view's bookmark star sits before the title (`starBeforeTitle` and `documentStar` in `public/project-layout.js`). On iPad (touch screens wider than phones) List, Tree, Table and Kanban also move search, filters and sort into the middle of the top bar (`topBarTools`); the row keeps the view's other controls and goes when none are left. Sort is an icon menu in every view, Table's included, and on/off options are checkboxes before their name (`.check-control`). In Calendar the controls every layout shares (weekends, Layout) come last on the right, after the layout's own controls and a divider (`.planning-separator`); Agenda's range is one menu of dates and quick ranges (`rangePicker` in `public/calendar.js`). Don't add a second bar for a view's controls.
- The board bar ends like the document bar, with Board tools (⋯), after the bookmark star on phones; before them sits who is here (avatars, `#canvas-presence`; beside View options on phones). Board tools is an icon menu (`iconMenu` in `public/project-layout.js`) that leads with Present and Board session, then Activity, History and Local checkpoints, then the board's actions, in groups split by dividers; each extra in `#canvas-extras` names its group (session, history or tools) with `data-menu-home`; there is no More and no Session or Version history menu. On desktop, Board appearance sits directly before Board tools in the board bar; touch screens and full-screen boards keep it in their canvas controls. The board's other tools sit in the left tool bar, as icons only (each group named for screen readers): Frames (the outline, with Layers as its second tab), Live task view and an Insert menu that opens beside the bar; phones dock the tools as categories (Navigate, Add, Pen, Search; `public/phone-board-tools.js`), with Insert's actions in Add's row, and a category shows the tool chosen in its row. The chosen tool is filled in the accent colour. Connections is in Board tools, after Link cards, with the selected object as From.
- Documents have one bar: formatting on the left, always shown except in Reading view; on the right Properties (its own contextual dropdown), Focus mode and ⋯ (Document tools), after the bookmark star on phones, which holds the document views (Live preview, Source, Reading) and every other document action once, in groups split by dividers; on desktop and iPad the open documents' tabs take the title's place in the top bar, in the title's type (the heading stays for screen readers), and phones show no title. Focus mode temporarily shows only the document and its exit icon, hiding surrounding navigation, formatting and secondary panes without rebuilding editors. Its icon or Escape restores the layout; Escape closes an editor search or popup first, and save problems stay visible.
- Use one sidebar, and keep view-specific navigation out of it. The document list and the board list have a page of their own (`#list-panel`, `public/list-panel.js`), opened by pressing the open Documents or Boards tab (on touch screens with a document open, the Documents button in its tray): on desktop and iPad it covers four fifths of the page from the left, with the open document or board blurred beside it, and phones show it as a full page; a choice, Escape (after clearing its search), its close button or a click outside closes it; a board choice closes it only once accepted. Both lists share the folder tree (`public/folder-tree.js`) and its panels (`public/anchored-panel.js`): documents have a ⋯ menu like folders (Rename, Move to folder, Delete, for any document), Import Markdown is an icon in the list's header, and on touch screens a long press opens a row's menu (a folder's panel) as the finger lifts, while a long press then a move drags it onto a folder. Don't add a second sidebar or menu button for one view. On phones and touch screens such as iPad (`tabBar` in `public/layout-tray.js`, matching `(max-width: 600px), (pointer: coarse)`) the top bar's view tabs become a floating, rounded bottom bar of icons (Home, Overview, Documents, Planning, Tasks, Boards, then the person's own buttons (`public/bottom-bar.js`: commands and bookmarks, set in Settings → You or with a long press on the bar, kept per person by `server/bar.js`), a divider and Search, which opens the search dialog; the bar scrolls sideways inside `.tabs-scroll` when they don't fit; desktop shows the same Search button after the view tabs in the top bar, and no own buttons), at most 480px wide and centred on iPad, that hides while typing; pages, boards and documents run under it, and their controls at the bottom sit above it (`--tabbar-clearance`, `--board-bottom-clear` on the board); tapping the open Tasks, Planning or Documents tab again shows a tray above the bar (`.layout-tray`, mounted with `public/layout-tray.js`); desktop uses the same tray below the top navigation when pressing its active tab again: the Tasks or Planning layouts, or Documents (the document list), a divider and the document views (Live preview, Source, Reading). With no document open, tapping the open Documents tab opens the document list. The sidebar opens over the content on every device, sliding in from the top bar's menu button (315px wide on iPad), and closes with Escape, its close button, a click or tap outside or a choice; it never moves or narrows the page (phones blur the page behind it). It starts with Home (each person's page of panels, `public/home.js`, kept per person by `server/home.js`; the app opens on it and the brand returns to it), Personal and Today, then Organisation and Projects, each a title with + on its right over a dropdown (`.sidebar-switch`) whose menu takes the sidebar's dark colours (`.sidebar-select-menu`), with Settings, Roadmap (the internal list of requests in `public/roadmap.js`, shown as a help page and updated with every release) and Help, then the version at the bottom; don't put views back in it. The personal space is a documents-only project (`personal: <username>`): it shows only the Documents view, the You settings and Trash.
- On touch screens, only a tap on a text field may open the keyboard. Search is the exception: opened from its button or Ctrl/⌘ K, it focuses its field at once, within the tap (`searchDialog` in `public/features.js`), so phones show the keyboard. Move focus into text with `focusOnOpen` (`public/open-focus.js`), which leaves it on the control on touch. Controls placed inside an editable area rely on `public/editable-controls.js`, because iOS Safari focuses the editor when such a button is tapped. `reports/assets/ui-ux-2026-10-27/scripts/keyboard-audit.mjs` checks every view.
- A project can turn off any built-in card field but the ID and title (`off` in its schema, Settings → Statuses & workflow → Card fields; `public/card-fields.js`): the root's `data-fields-off` hides it everywhere through `public/card-fields.css`, so give a new field surface a hook there; filters, sort, grouping and Table columns leave it, and views that need it leave the tabs (`viewOn`). Values stay in the files. With Parent off the placement rules wait (`canParent`); with estimates off Capacity counts tasks.
- A project can also turn off views and whole components (`views_off` in its schema, Settings → Views; `VIEW_GROUPS` and `viewOn` in `public/card-fields.js`); Overview always stays. Filter any new list of views, tabs or New menu items through `viewOn` (tabs through `areaOn` in `public/app.js`, new cards through `cardsOn`).
- Show task fields in one order in every component: card type, ID, assignee, status, priority (then dates). This covers List/Tree rows, phone summaries, the card editor, relationship rows and pickers, board task cards and default Table columns. Where space is tight, show the assignee as an avatar only (the short name set in Settings → Organisation, or else the name's first three letters: `shortName` in `public/teams.js`) and keep the name in its accessible label and tooltip.
- Wherever assignee, status and priority appear together they sit in one box (`field-box`, with `fieldBoxStyle` from `public/task-colors.js`), with the date, where shown, after the priority in the same box (List and Tree rows, phone summaries, where it opens the date editor like the other fields, relationship rows, Kanban and board cards): a neutral surface fill, a 1px border in the priority's colour and the shared `--field-radius` corners. Priority colours are a project setting (Settings → Workflow), with the defaults in `task-colors.js`. Fields inside the box have no border or fill of their own and show their value's colour on the text (assignee avatars are rounded squares, not circles). Table cells, which hold one field each, keep a single-field chip with the value's colour on its border and text. The card editor shows the fields at control height. Lists (List and Tree rows, relationships, Table, Kanban) use the smaller list chip from `--list-field-*` (24px, 32px on touch), centred inside a full-height 32px/44px target so there is room above and below. List and Tree rows draw their box at list-chip height behind the full-height targets. On phones the box has one width (216px with all four fields, at least 176px for their 44px targets) at the end of List and Tree rows and relationship rows, so the boxes line up and the card ID keeps the rest of the line. A box is as wide as the fields the project shows: widths count each field through `--box-*` in `public/card-fields.css` (sum the fields' widths; WebKit sizes a `max-content` box from its text). Use the `field-chip` and `field-box` classes and the shared rules at the end of `public/controls.css` instead of styling these fields per view. Board cards keep their document-scale size with the same shape. In List and Tree rows the title follows the ID.

- Deleted cards, documents and boards stay in Settings → Trash for 30 days (`projectTrash` and `purgeTrash` in `server/recovery.js`), and committed changes enter the project's audit log through `Store.auditRecord()` (`server/store.js`, `server/audit.js`, kept 365 days). Routes use `ctx.mutate()` to pass the actor; background writers use `store.mutate()` and the shared record methods. A direct file writer must call `auditRecord()` inside that transaction; never log an uncommitted change or repeat the entry in the route.

- Personal shortcuts live in Settings → You → Hotkeys (`public/hotkeys.js`), reuse the command and bookmark actions, and are stored per person by `server/hotkeys.js`. Keep browser tab shortcuts available, reject conflicting bindings, and do not run custom shortcuts while typing or editing a card.
- New projects use the three-step dialog in `public/project-create.js`: Details (including organisation teams under People), Card types & hierarchy, then Workflow. Reuse the settings type controls and workflow editor; keep all entries and browser drafts between steps, validate before advancing, and create the project only on the final step.

## Dialogs and contextual panels

- Prefer small, contextual panels near the component or action that opened them. Reuse the shared panel styles, positioning and keyboard behaviour.
- Keep the surrounding page usable for routine actions; support dismissal with Escape, a close button and clicking or tapping outside.
- Use blocking or fullscreen dialogs only when interaction must be stopped for a warning, a major action or another substantial workflow. Do not default to a large centered modal for a small operation.
- Keep panels within the viewport on desktop, iPad and mobile, with scrolling inside the panel when needed. On phones and iPad they end above the bottom bar: `positionPopover` (`public/popover-position.js`) stops at `bottomBarTop` and board menus at `boardFloor` (`public/layout-tray.js`), so place new panels with them.

## Changelog

- Update `CHANGELOG.md` in the same change as every user-facing addition, change or fix.
- Record each feature's actual Requested, Started and Done timestamps in `public/roadmap.js`, preferably as ISO timestamps with an offset, plus the primary coding model and reasoning effort used. Took measures elapsed wall time (including planning, queueing and checks), not active model runtime. Historical backfills must name their basis (for example first recorded response or release commit); leave unrecorded values missing instead of inventing times or model settings. A setting saved before a gap in the session logs does not establish the coding model used during that gap. Releases from 0.21.67 require complete tracking metadata.
- Keep newest entries first, grouped by version and date (`YYYY-MM-DD`, Europe/London). Describe the user-visible result under Added, Changed or Fixed as appropriate.
- Put work not yet released under Unreleased; assign its release date when deployed. Keep the version consistent with `package.json`.
- Preserve historical entries. If backfilling history, distinguish the date recorded from the actual release date; do not invent dates or version mappings.

## Testing

- `npm run check` (syntax, types) and `npm test` (unit) take seconds; run them on every change, text-only edits to a `.js` file (such as help content) included. Write the failing test for a new route, module or rule before its code. Browser tests are Playwright Test specs in `e2e/<area>/` (`npm run e2e`, or a folder, file or `-g` title filter).
- `npm run release` runs the browser tests a change needs: `scripts/affected.mjs` maps the files changed since the last release commit to areas (a module counts for every area whose code imports it), adding `e2e/ui` (sizing, visual rules, accessibility) for any change to `public/`. Shared code and shared styling (`controls.css`, `styles.css`, `appearance.css`, `enhancements.css`, `project-layout.*`, `app.js`, `features.js`, `server/`) run every test, and so does a file the map doesn't know. `npm run e2e:affected` runs the same selection while you work. Add new source files to the map. The map works by file, so a component stylesheet edit that changes `:root` tokens or element-wide selectors needs `npm run e2e` instead.
- The `@heavy` scale tests (100,000-object boards, thousands of pasted objects, 100 members) run in the batch check, or with `HEAVY=1`; the map adds them when board data, selection or server code changes.
- Run browser tests locally with `--project=chromium`. Phone and iPad tests (`onDevices` tags them `@touch`) also run in WebKit, the iPhone's engine, in the `ios` project, which `npm run release` includes (`IOS=0` skips it); `scripts/webkit-local.sh` adds the libraries WebKit lacks on a host without sudo. A test that needs Chromium's DevTools protocol skips in other engines; a known WebKit difference is marked `test.fail(browserName === "webkit", reason)` until fixed.
- Judge a run by Playwright's summary (its failed and flaky counts) or the test command's own exit status, never by the exit status of a pipeline that ends in `tail` or `grep`.
- Keep every test passing. When a change in intended behaviour breaks a test, update it in the same change. Never leave a test failing; a known bug may be marked `test.fail()` with its reason until fixed.
- Write tests with `e2e/fixtures.mjs` (`useApp`, `onDevices`, device presets) as described in `e2e/README.md`. Wait for page state with web-first assertions instead of fixed delays. Tests fail on console and server errors; allow expected ones with `test.use({ allowErrors })`. Seeded dates don't move with today: go back to them after a reload.
- Specs started with `productionAssets` serve the built `dist/`: run `npm run build` before `npm run e2e` or `npm run release` after changing `public/`, or they test the old build.
- When splitting or escaping Markdown by hand (table cells, links), check edge cases such as `\|` and `\\|` against marked's own output, and test them.
- Before moving a container's edge (such as letting content run under the bottom bar), grep for what is anchored to that edge (`bottom:` rules, `clientHeight -` sums) and move it too.
- The fixtures reduce motion. A change that animates only when motion is allowed needs a test that turns it on (`page.emulateMedia({ reducedMotion: "no-preference" })`) and runs the flows through it, not just the animation.
- A visual change asserts the computed style it sets (`getComputedStyle`), not only attributes or text. Where engines may read the CSS differently (SVG properties, `calc()`, newer features), tag the test `@gate` and run it in Firefox and WebKit before releasing (`GATE_BROWSERS=firefox,webkit npx playwright test <spec> --project=firefox --project=webkit`).
- A module that unit tests import, directly or through another module, reads `window`, `document` and `matchMedia` inside functions, never at its top level; listeners it needs are installed from `app.js` (as `installDebugLog()` is).
- Audits, which report findings instead of guarding a change (such as `ui-assessment`), are tagged `@audit` and run only with `--project=audit`.
- Two reports show where tests are thin: `npm run e2e:coverage` (how much of each `public/` module the browser tests run, and the modules no page loads) and `npm run test:mutants` (small faults put into the journal, store, model and write access, or the modules named, that no unit test notices). Run the mutants after changing a data or access rule and cover what survives, unless the fault can't change behaviour.

## Deployment

- Versioning starts from the `0.21.0` baseline (owner request, 2 November 2026). Each future feature/change has a number from 1 to 100 within its major/minor cycle, recorded in `public/roadmap.js` and the changelog with a unique ID such as `F0.21-1`. Keep historical T IDs and release versions intact; the baseline itself consumes no feature number. Release one completed numbered feature per patch increment: `F0.21-1` → `0.21.1`, `F0.21-99` → `0.21.99`, `F0.21-100` → `0.22.0`, then restart at `F0.22-1` → `0.22.1`. The release command rolls `.99` to the next minor's `.0` and checks the matching completed roadmap entry. Major versions change only on explicit request; use `npm run release -- patch` for routine releases, including the automatic rollover.
- Deploy each completed new feature as soon as its relevant checks pass, within the same task.
- This is standing authorization to deploy to the existing Pencils environment; do not wait for a separate deployment request or confirmation unless the user explicitly asks to hold deployment.
- Write the user-visible changes under `## Unreleased` in `CHANGELOG.md`, then release with `npm run release -- patch`. It runs the checks, unit tests and the browser tests the change needs, sets the version everywhere, dates the changelog, keeps the vault and container settings, tags `pencils:rollback-before-<version>`, waits for `/api/health` to report the new version (restoring the previous image if it doesn't) and tags `pencils:release-<version>`.
- After each healthy release, retain only three distinct Pencils Docker images: the live release and two previous images, preserving the exact immediate rollback image. The release script removes older `pencils:*` images and their release, rollback and legacy tags. Never force removal, delete images used by another container, touch other image repositories or volumes, or run a daemon-wide prune. Report cleanup failures or images skipped because they are in use; do not undo a healthy release because cleanup failed.
- When the queue of requested changes is empty, run the batch check before the final report: `GATE_BROWSERS=<installed engines> npm run test:release` (every test including `@heavy`, the `@gate` tests in Firefox/WebKit and the Docker check). Fix any failure with a patch release.
- Verify the running version and application health after deployment. Report any blocker clearly and distinguish local changes from changes that are live.
- When a new version is released, commit it and push it to the remote (`origin`).
